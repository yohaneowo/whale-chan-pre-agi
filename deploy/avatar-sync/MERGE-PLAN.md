## 2. 怎么合并（只追加、不重复、出处保留）

原则：**不改写任何现有的字节**；只往末尾追加；已有的不重复；每一行／每个档案都逐字节照原样，不加标记、不改内容（帐本是「原文帐本」，不插入非讯息行）。合并记录（哪些行、来自哪次开机、前后 sha256）放在**本机**，不放进线上的档案。

**前置条件**（全部满足才动手）：(1) 老板批准；(2) pve2 的网路已修好并观察一段时间（建议至少 24 小时没有 `nic0: Link is Down`）；(3) 有人（Sora／老板）**看过**那 3 则记忆和 3 行人物卡的内容再决定（里面有聊天内容，我没读，也不会贴）；(4) 同步 routine 仍然暂停；(5) Rin 审过合并脚本。

**写入线上有竞争**：帐本是 dsh 的 `appendFileSync`，人物卡是 dsh 整档重写。所以合并要在 **dsh 服务停止的一小段时间**（预计不到 1 分钟，她会离线那么久）里做，不然人物卡可能被 dsh 的重写盖掉。

步骤（脚本先做成「演练模式」：只在本机比对、印出会做什么，不写线上；Rin 审过才开放实写）：

0. **先拍 PVE 快照**（pve2 的 VM 102，项目规则：动线上之前先 snapshot）。记下合并前三个目标的 sha256（帐本日档、两张人物卡）与大小。
1. **停 dsh**（`systemctl stop dsh`，`dsh-secrets` 不动）。
2. **帐本**：对照线上现有的 `archive/2026-11-10.jsonl`，用 (kind, id, t) 去重（已有的那 1 行跳过），把「只在旧副本」的 42 行**按原样、原来的相对顺序**（先 message 后 edit）追加到文件**末尾**。追加前确认文件以换行结尾；不插入中间。
   - 这样旧内容仍然是新内容的开头：dsh 的追加方式不受影响，**也满足同步脚本的来源连续性检查**（下一次同步会看到「只追加」）。
   - 代价：该日档不再按时间排序。读取端（`deploy/social/archive.mjs`）有几处会自己按 `t` 排序（我只用 grep 看到 `sort` 的位置，**没有逐条验证**每条读取路径是否依赖行序，例如「最后一笔」「某笔前后」这类）；列为 Rin 要审的重点，审不过就改成「停服务时把整个日档按时间重排」（那就不是纯追加，要另外评估对同步连续性检查的影响）。
3. **记忆 3 则**：把 3 个 uuid 档案（逐字节）放进 `memory/ad936fcb…/`（先确认不存在同名）。它们的 `messageId` 指向第 2 步追加的讯息，所以**必须在第 2 步之后**；否则出处核对会把它们当成「来源不见了」而不带进提示。
4. **人物卡 3 行**：不覆盖整档。只把「只在旧副本」的那 3 行插到线上同一张卡、同一节（`## 知道的事`）的末尾，其余字节不动；同一行已存在就不加。它们的 `src::` 指向第 2 步的讯息。
5. **启动 dsh**，确认 active、gateway ready、日志没有 error（只看日志，不发消息）。
6. **验证**：用同步脚本的 fetch 只读抓一次线上资料（不写本机镜像），跑 `check_continuity`：帐本日档应该是「只追加」、`violations: 0`；3 则记忆是新增档案。再用出处核对确认那 3 则记忆会被带进提示（`MemoryStore.visible`）。
7. **记录**：合并脚本的输出（追加了几行、哪些略过、前后 sha256）存本机；在知识库 `raw/inbox/` 留一份纪要（不动 wiki）。**合并完成并观察一阵子之后**才由 Sora 决定恢复同步 routine。

## 3. 风险

- **在线上写入**：唯一一次对线上资料的写入。快照与「只追加」把范围压到最小；仍然是写入，所以要批准。
- **竞争**：不停 dsh 做的话，人物卡可能被重写盖掉，帐本追加可能和 dsh 的追加交错——所以要停服务做。
- **内容的正确性**：那 3 则记忆和 3 行人物卡是旧副本在十一天前的世界里推出来的，可能和线上后来的更正冲突（线上有 11-09 之前的 125／155 行新卡片内容）。要人看过再合（前置条件 3）。5 笔发言也是基于旧记忆，其中可能有错的说法；合并只是让她「记得说过」，不修正内容。
- **帐本不按时间排序**：见上，读取端没有逐条验证过。
- **重复**：用 (kind, id, t) 去重；只发现 1 行重复。如果线上在合并前又收到新的讯息，会排在末尾，不影响。
- **隐私**：群聊内容只在本机备份与线上；方案、回报、日志都不贴内容。
- **同步**：合并期间与观察期间同步 routine 保持暂停；合并后第一次同步应该通过连续性检查（只追加）。若没有通过，先看原因，不要加 `--accept-source-change`。

## 4. 回滚

- **刚合并完发现问题**：最快是 `qm rollback` 回到第 0 步的快照（pve2 的 VM 102）——代价是快照之后线上所有新资料一起丢掉，所以只适用于「合并完马上发现」。
- **精细回滚（合并后 dsh 已经又写了新东西）**：停 dsh → 从帐本移除「合并脚本记录的那 42 行」（逐行精确比对，不动其他行）→ 删除那 3 个记忆 uuid 档案 → 从两张人物卡移除那 3 行（精确比对）→ 核对帐本／人物卡的 sha256 等于「合并前的内容 + dsh 合并后新增的行」→ 启动 dsh。需要老板批准（因为是删除线上的资料）；脚本提供 `--unmerge`，同样先演练。
- **同步端**：如果合并后同步已经跑过，回滚会让帐本变短、被来源连续性检查拦下；确认回滚是预期的之后，才由人加 `--accept-source-change`（并且回到较早的内容时，要两个旗标都明讲）。本机镜像在合并前不会被动到，所以暂停同步期间不需要回滚它。
- 旧副本的磁碟、快照与本机备份**一律保留**，直到老板另外决定。
