## 2. 拟人性与架构改进分析

### 2.1 群聊交互自然感（Naturalness & Pacing）
* **现状评估**：
	* 对照 `docs/research/social-persona-and-naturalness-review.md`，此前暴露的「括号动作描写」、「逐条作答（Checklist Bias）」、「高频自称本鱼/叫主人」已通过 `persona-group.md`（繁体、约 1.4 千字）与短句指引得到大幅改善。
* **核心短板：缺乏连续短句节奏（Burst Messaging）**：
	* **痛点**：目前 `bridge.mjs` 送往 Discord 的文字是一次性交付。即便提示词要求「二三十字以内的短句」，模型在稍微复杂的表达中仍会输出 2~3 行。在 Discord 客户端上，这会表现为瞬间弹出一整块文字，机器感显著。
	* **改进方案**：
		1. **行/标点智能切分**：在 `prepareGroupReply` 之后，将多行文本切分为 1~3 条独立的短消息。
		2. **拟态打字（Typing Simulation）**：调用 Discord REST 接口发送 `sendTyping`，第一条短消息（如吐槽、应答短语）在 300ms~600ms 内秒发，第二条补充消息延时 800ms~1500ms 发送，完美模拟真人在即时通讯软件中的打字节奏。
* **去客服感与主语省略**：
	* 提示词中已明确加入日常台湾口语指引（「辛苦啦」「在啦在啦」「叫我幹嘛」）。
	* 建议在 `natural-participation.mjs` 的消息聚拢窗口中，进一步强化对同一用户连发多条短消息时的聚合处理，向模型注入 `[連發中：使用者正快速輸入]` 标记，引导模型仅回复最后一句话的核心槽点。

### 2.2 长期记忆系统运作效率与一致性（Long-term Memory & Provenance）
* **架构机制剖析**：
	* 采用 Markdown 散列小文件存储记忆正本，按频道与私人范围隔离；
	* `archive.mjs` 的 `collapseRevised` 与 `judgeSources` 提供了目前行业内罕见的消息版本溯源机制：不仅记住了什么，更记住了「谁在哪个消息 ID 说的」。
* **扩展性瓶颈与优化方向**：
	1. **小文件 I/O 隐患**：`all(scope)` 每次通过 `readdirSync` 读取该 scope 下所有 `[uuid].md`。当单个群聊运行数月、积累上千条记忆记录时，磁盘 I/O 开销将显著增加。
	2. **演化方案（SQLite 辅助索引层）**：
		* 严格保持 Markdown 为**唯一数据正本**（可被 Obsidian 随时浏览与 Git 版本化）；
		* 引入轻量级本地 SQLite 数据库作为只读缓存索引（含 `fts5` 分词表与元数据列：`id, at, messageId, hash, text`）；
		* 启动或写入时通过文件哈希进行增量同步，将检索时间复杂度从 $O(N)$ 降至 $O(\log N)$。

### 2.3 用量护栏与前缀缓存（Prefix Cache）最佳化空间
* **DeepSeek Prompt Cache 经济学**：
	* DeepSeek 官方对命中的前缀缓存收费极低（以 Flash 为例：未命中 $0.14 / M Tokens，命中仅 $0.0028 / M Tokens，相差 50 倍）。
* **当前潜在击穿点排查**：
	* 提示词组装顺序直接影响缓存前缀的稳定性。
	* **现状排查**：当前聊天记录头部如果过早引入了动态变化的高频信息（如精准到秒的当前时钟、动态波动的剩余饭钱、每轮不同的活跃用户 ID 列表），会导致后续大部分静态提示词无法命中前缀缓存。
* **重构优化建议**：
	* 严格实行「静态靠前、动态靠后」的布局：
		1. 第一层（100% 静态）：`persona-group.md` 全文 + 核心行为规范 + 工具定义；
		2. 第二层（准静态）：`facts.md` 长期稳定事实；
		3. 第三层（低频更新）：近期活跃成员的固定人物卡；
		4. 第四层（高频动态 - Cache Boundary）：当前时间戳、当前剩余饭钱、召回的即时事件记忆；
		5. 第五层（纯动态尾部）：最近的群聊上下文新消息。
	* 调整后，前 3 层的内容可长效驻留在 DeepSeek 边缘节点的 Prefix Cache 中，单次群聊调用成本可下降 60%~80%。

## 3. 创新 dsh（DeepSeek Harness）插件概念构想

结合 deepseek-harness 的 Cordis 微内核架构、生命周期钩子（Events）与服务注入能力，提出以下两个高可行性、高拟人价值的全新插件概念：

### 概念一：`dsh-plugin-reaction-animator`（微表情与轻社交反应堆插件）

* **【解决痛点】**：
	* 真人群聊中，成员并非对每一句话都打字回复；面对沙雕图、搞笑吐槽、打卡或群内通知，真人群友通常习惯「随手点个 Reaction 表情」或「贴表情回应」。
	* 目前鲸鱼娘要么触发完整 LLM 回合打字回复，要么保持绝对沉默，缺乏「轻量化在场感」，且频繁调用 LLM 浪费饭钱。
* **【核心机制与事件钩子】**：
	1. **Cordis 事件拦截**：监听 `discord/message-create` 事件，位于 `natural-participation` 决策流水线的最前沿。
	2. **轻量启发式规则引擎（Zero-LLM Cost）**：
		* 当检测到图片/动图（Meme）且群内讨论热烈时，根据文字关键词或图片类型触发概率点表情（如 🐟、😂、👀、🫡、💯）；
		* 当站长或群主发布通知、改动规则时，秒点 🫡 或 🆗；
		* 深夜检测到群友「睡了」「晚安」时，点 💤。
	3. **调用现成原生接口**：直接复用 `deploy/social/discord-tools.mjs` 中的 `discord_add_reaction`，设置 500ms~2000ms 随机延时模拟手速。
* **【拟人化价值】**：
	* 以零 Token 消耗维持高度拟真的群聊「摸鱼在线感」，群友能即时感知到「小鲸鱼正在看着群里，并给你的发言点了赞/翻了个白眼」，大幅增强陪伴体验。
* **【实装难度评估】**：
	* **低（Low）**。底层已有完整的 `discord_add_reaction` 与上下文身份支持，仅需编写约 120 行的 Cordis 插件中间件与配置表。

---

### 概念二：`dsh-plugin-whaledraw-atelier`（鲸鱼画坊动态画板与群友互动合影插件）

* **【解决痛点】**：
	* 目前 `deploy/draw/whaledraw` 具备成熟的场景与零件合成能力，但使用方式非常底层（要求模型自己编写并执行一段 Python 代码并处理 `publish`）。
	* 模型在群聊中直接手写 Python 容易因语法错误、图层重叠（Overlap Check Failure）或坐标偏差导致一轮交互失败，且群友无法直观参与合照与互动。
* **【核心机制与事件钩子】**：
	1. **Cordis 上下文高阶工具注入**：
		* 向群聊会话动态注入轻量意图工具 `atelier_compose`：
			* 参数：`pose`（预审封印姿势，如 "eating"、"hugging"、"proud"）、`prop`（道具，如 "rice_bowl"、"keyboard"）、`companion_discord_id`（可选合影对象）。
	2. **头像与立绘自动化流水线**：
		* 若指定了合影群友，插件自动调用 `deploy/avatar-sync/` 拉取该用户的 Discord 头像圆图，作为 `whaledraw` 的道具部件（Prop）；
		* 自动调用预编译好的 Python 场景模板，自动计算安全锚点（`scene.anchor`）与避让区域（`scene.free_spot`），消除重叠风险。
	3. **错误自愈与拟人化降级**：
		* 若立绘自检未通过，拦截底层 Traceback，向模型注入拟人反馈事件（例如：「衣服被呆毛卡住了」），驱动角色在群内以傲娇口吻自然解释，并降级发送台词梗图 `[梗圖:得加钱]`。
* **【拟人化价值】**：
	* 将冷冰冰的代码绘图转变为趣味性极强的「群友特调互动工坊」，群友可以随时叫小鲸鱼「画一张你抱着我的头像吃白饭的图」，生成具备合法版权的 Q 版合影，极大提高社群粘性与二次传播力。
* **【实装难度评估】**：
	* **中等（Medium）**。需在 `deploy/social/` 中封装对 `deploy/draw/` 的 Python 子进程标准化调用，并串联 `avatar-sync` 模块。
